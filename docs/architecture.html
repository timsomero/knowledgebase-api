TFAssist architecture

One ASP.NET Core service on Cloud Run serves both the web app and its API, keeps everything in Firestore, signs you in with Google, tidies up new tasks with Claude, and redeploys itself from GitHub whenever main changes.

The whole system

Five places are involved: your devices, Google's sign-in service, your Google Cloud project, GitHub, and Anthropic's Claude API. Everything you see and save goes through the one Cloud Run service.

Every request goes through the same checks in Program.cs, in this order. The choice between Firestore and in-memory storage is made once, at startup.

How sign-in works

Google's ID tokens expire after an hour, so the app uses one only to start a session. After that, the browser carries a cookie the service signed itself.

From a terminal

gcloud auth print-identity-token gives a Google token for your account. Send it as Authorization: Bearer … on every request; no cookie is involved. The service accepts tokens from both the web app's OAuth client and gcloud's.

Sign out everywhere

Deleting the dataProtectionKeys collection in the Firestore console invalidates every session cookie at once. The next visit on each device asks for Google sign-in again.

How a new task gets tidied up

Adding a task never waits on the AI. The task is saved exactly as typed, and the page asks for the tidy-up separately, so you can type or dictate the next one straight away.

Saved first, tidied second

The task is stored before Claude is involved, so nothing is lost if the tidy-up fails. No key, an outage, a 30-second timeout or an odd answer all mean the task stays as typed.

Your choices win

Notes, due date and tags are filled only while empty, and priority only while it is normal. A task you edit or complete before the answer arrives is left alone.

Tags never get invented

Claude chooses from the tags already on your tasks, done ones included. Adding a tag to any task by hand makes it available for the next one.

What's stored in Firestore

Each collection holds plain documents. The service reads whole collections and sorts in memory, which is fine at personal scale and needs no indexes.

The web app

The web app is one HTML page with plain JavaScript and no framework or build step. The part of the URL after # picks the screen, so the phone's back button moves between screens.

Styles live in app.css, with light and dark themes. The footer shows the running build ("Build N · commit") and offers a reload when the server runs a newer one. manifest.webmanifest and icon.svg make it installable as "TFAssist" on a home screen.

How a change reaches the live app

No one deploys by hand any more. GitHub proves its identity to Google for each run, so there are no passwords or key files to leak.

Worth knowing

  • No backups yet. Firestore point-in-time recovery or scheduled backups aren't turned on, so a deleted task or workout can't be recovered.
  • No automated tests in the repo. Each change was tested by hand and with throwaway browser scripts. The only CI check is that the code builds.
  • Task text goes to Anthropic. Each new task's text is sent to the Claude API to be tidied up, along with your tag names; nothing else is. Check that's fine for work tasks.
  • Single region. Cloud Run and Firestore both run in us-central1; an outage there takes the app down.
  • Whole-collection reads. Lists load every document and sort in memory. That's fine for one person; years of heavy logging would eventually want Firestore queries and indexes.
  • GitHub Actions warning. The workflow's actions run on an older Node.js version GitHub is phasing out; bumping their versions is a small follow-up.
